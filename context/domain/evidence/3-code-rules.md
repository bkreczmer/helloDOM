Zakres: całe repo (jedna aplikacja), wg `context/domain/evidence/0-sources.md`. Warstwy przeszukane:
`supabase/migrations/*.sql` (wszystkie 8), `supabase/config.toml` (auth), `wrangler.jsonc`, `src/middleware.ts`,
`src/lib/**`, `src/pages/api/**`, `src/pages/{owner,agent,auth}/**`, `src/pages/dashboard.ts`, komponenty z formularzami
i potwierdzeniami (`src/components/{owner,agent,account,auth}/**`), testy `supabase/tests/*.sql`,
`tests/integration/*.ts`, `tests/e2e/*.spec.ts` (tylko nazwy testów), `scripts/smoke.mjs` (tylko komentarze).
Wzorce: `check`, `unique`, `references … on delete`, `create policy`, `grant`, `for update`, `raise`/kody wyników RPC,
`z.` schematy, `profile?.role !==`, `disabled`, `CONFIRM_TEXT`, `cron|scheduled|queue|expires`.
Nie czytano: `context/**` poza `0-sources.md`, `README.md`, `CLAUDE.md`, `AGENTS.md`, `src/db/database.types.ts`.
Nie pokryto szczegółowo: treści kroków `scripts/smoke.mjs` i ciał testów E2E (tylko tytuły), `src/components/ui/**`, layoutów.

Wyjaśnienie: kolumna „reguła” to moje sformułowanie (**inference**); cytaty w backtickach to słowa źródła.
Wszystkie lokalizacje sprawdzone w tej sesji. Etykieta przy wierszu: E = evidence, I = inference.

## Soft and client-only rules

1. **Ranking tylko dla oferty `seeking_agent`** — soft. Strona woła RPC tylko przy `seeking_agent` (`src/pages/owner/offers/[id].astro:60`), ale `rank_agents_for_offer` nie filtruje statusu (`invitation_response.sql:42-49`). Ścieżka obejścia: bezpośrednie RPC; test to potwierdza — `isolation.test.ts:103` (I2) oczekuje rankingu oferty X, która w `:100` (I1) ma status `invited`. Skutek ograniczony: zaproszenie i tak blokuje `invite_agent` (`create_invitations.sql:87-89`). (E dla zachowania, I dla oceny)
2. **Agent nie poznaje tożsamości właściciela** — soft. Strona agenta nie wybiera `owner_id` (`src/pages/agent/offers/[id].astro:14-15`: „owner_id is not selected, so no owner data leaks”), ale grant `select` obejmuje wszystkie kolumny `offers` (`create_offers.sql:42`), a agent czyta też `invitations.owner_id` (`create_invitations.sql:14,40-43`). Obejście: zapytanie z kluczem anon i sesją agenta o `owner_id`. Ujawnia tylko uuid; profil właściciela pozostaje niewidoczny (`create_profiles.sql:14-17`). (I)
3. **Powtórzenie hasła przy rejestracji** — client-only: `auth-schemas.ts:14` („confirmPassword is validated on the client only”), `SignUpForm.tsx:56-59`. Bez znaczenia biznesowego.
4. **Potwierdzenia nieodwracalnych akcji** (usunięcie oferty, usunięcie konta, przyjęcie/odrzucenie) — client-only: `DeleteOffer.tsx:22-27`, `DeleteAccount.tsx:13-16`, `InvitationResponse.tsx:14-17`. Endpointy nie wymagają potwierdzenia (UX, nie reguła danych).
5. **Limit 50 pozycji na listach** — tylko odczyt/UI: `offers.ts:22-23` (`OWNER_OFFERS_LIMIT`), `invitations.ts:7-8` (`AGENT_INVITATIONS_LIMIT`). Brak limitu liczby ofert właściciela w danych (szukano `limit|count` w migracjach — nic). (I)
6. Reguła „jeden aktywny agent na ofertę” jest pilnowana także dla zapisów `postgres` (indeks), więc nie jest soft.

## Writers that work against a guard

- **Trigger `restore_offer_on_invitation_delete`** (`account_deletion.sql:11-34`) zmienia `offers.status` poza RPC zaproszeń, mimo zasady „status changes only through the invitation RPCs” (`owner_offer_management.sql:3-5`). Celowy wyjątek (security definer, tylko przez trigger: `account_deletion.sql:28-29`). Może przenieść ofertę z `in_progress` z powrotem do `seeking_agent` — jedyna droga wyjścia z `in_progress` poza usunięciem oferty (I: nie znaleziono innego zapisu z `in_progress`).
- **Jednorazowa naprawa danych w migracji** (`account_deletion.sql:36-45`): `update public.offers set status = 'seeking_agent'` dla osieroconych ofert; „the down block does not undo it” (`:37-38`).
- Bloki `-- down:` cofające statusy ręcznie (`create_invitations.sql:119-120`) — instrukcja dla człowieka, nie kod wykonywany.
- Nie znaleziono w `src/**` użycia `service_role` (szukano `service_role|SERVICE` w `src/`); wszystkie endpointy używają `createClient(context.request.headers, context.cookies)`, czyli sesji użytkownika (E dla wyszukiwania).

| operacja                                          | transakcja?                                                                                        | cytaty                                                          |

## Scheduled and asynchronous work

Przeszukano `src/**`, `supabase/migrations/*.sql`, `supabase/config.toml`, `wrangler.jsonc` pod kątem `cron|scheduled|queue|setTimeout|setInterval|expires|expiry`: brak harmonogramów, kolejek i handlerów `scheduled` (`wrangler.jsonc` nie ma `triggers`). Trafienia `jwt_expiry`/`otp_expiry` (`config.toml:158,219`) dotyczą Auth, nie domeny. Nie znaleziono reguły zależnej od czasu (np. wygasania zaproszeń): zaproszenie `pending` czeka bez limitu (I). Jedyna praca „później” to synchroniczny trigger `invitations_restore_offer_on_delete` (`account_deletion.sql:31-34`), podpięty do handlera.
